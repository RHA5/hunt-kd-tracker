# Управление историей обновлений (Changelog)

**ОБЯЗАТЕЛЬНОЕ ПОВЕДЕНИЕ:**
Всякий раз, когда вы (ИИ) успешно завершаете работу над существенным функционалом, крупным рефакторингом или важным исправлением багов в этом проекте, вы ОБЯЗАНЫ проактивно предложить пользователю обновить историю версий.

## Инструкции для ИИ:
1. **Когда триггериться**: После тестирования и финального утверждения пользователем любой значимой задачи (не касается мелких опечаток или разовых команд).
2. **Действие**: Перед тем как закончить диалог по текущей задаче, обязательно задайте пользователю вопрос: *"Стоит ли нам добавить информацию об этих изменениях в историю обновлений (changelog)?"*
3. **Реализация**: Если пользователь согласен, вы ОБЯЗАНЫ сначала прислать ему в чат **черновик текста** для новой версии (с указанием планируемого номера версии и даты).
4. **Стиль написания (Инфостиль)**: Тексты для changelog необходимо писать строго в инфостиле (в стиле Максима Ильяхова). Формулируйте тезисы кратко, опирайтесь на факты, пишите в мире читателя. Избегайте воды, канцелярита, стоп-слов и лишних прилагательных (например, вместо "добавлена совершенно новая крутая функция" пишите "добавили функцию").
5. **Утверждение**: ТОЛЬКО ПОСЛЕ того как пользователь скажет "согласовано" (или внесет свои правки), вы можете обновлять массив `changelog` внутри файла `changelog.js`.
6. **Версионирование ресурсов (Cache Busting)**: При обновлении версии в `changelog.js` (например, на `0.2.5`), обязательно обновляйте GET-параметр версии в тегах подключения скриптов во всех HTML-файлах: `<script src="changelog.js?v=0.2.5"></script>` и `<script src="supabase.js?v=0.2.5"></script>`. Это заставляет браузеры пользователей мгновенно загружать новый код без удержания устаревшего кэша.
